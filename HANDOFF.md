## 🧭 Lecciones permanentes (leer antes de citar el Excel o escribir una función SQL nueva)

- **`D-n` es la fila de la hoja `DICCIONARIO_CAMPOS` en el `.xlsx`** (encabezado en la fila 1; `D-2` es la primera fila de datos) — **nunca** la línea del CSV exportado por `scripts/metodologia/exportar_excel.py`. Ese CSV cita, con comillas y saltos de línea dentro de una celda (la columna "Validación y dependencias" es la más larga), por lo que una fila de la hoja ocupa varias líneas físicas del CSV y la numeración se desfasa del número de fila real desde aproximadamente la fila 33 en adelante (desfase confirmado de +10 hasta al menos la fila 267). **Antes de citar un `D-n`, verificar la fila real con `scripts/metodologia/fila_diccionario.py`** (lee el `.xlsx` con `openpyxl`, no el CSV) — nunca contar líneas del CSV ni asumir una correspondencia 1:1. Este error (AM-16 del roadmap invirtió el criterio y mandó usar la línea del CSV "en todo lo nuevo") se había propagado a las fichas CC-043 a CC-047, AM-15, los comentarios del motor de reglas y las migraciones 018b a 018d — corregido el 2026-10-23 (commit "docs: corrige citas D-n"). Las citas `D-n` son solo documentación (comentarios, mensajes de error, nombres de test): ningún código las usa para calcular ni para ramificar lógica.
- **Los tests de Jest simulan (mockean) la base de datos — nunca ejecutan una función SQL real contra PostGIS/Postgres.** Toda función SQL nueva necesita, además de los tests de Jest, al menos un caso por cada rama (cada formato, cada tipo de entrada) en un script SQL que se corra de verdad contra `valpo-verde-conecta-pruebas` antes de darla por buena.
- **Probar también cómo consumen el dato las funciones que vienen después, no solo la función nueva por separado.** El defecto de fondo de la 018d (#57) — el alta no creaba la versión en `tree_data_versions`, lo que `fn_refresh_tree_current` necesitaba como respaldo — solo apareció al encadenar alta → OT → `fn_refresh_tree_current`; ninguna prueba de la función sola lo habría detectado.
- **Al agregar parámetros a una función ya aplicada (ej. 018e → 018f), hay que `DROP` la firma anterior antes de `CREATE` la nueva**, aunque los parámetros nuevos tengan `DEFAULT`: Postgres identifica una función por su firma completa, así que sin el `DROP` quedan dos sobrecargas — la vieja (sin la validación nueva) sigue siendo invocable por cualquiera que la llame con la firma antigua. El `.down.sql` de esa migración debe revertir exactamente al revés (`DROP` la firma nueva, `CREATE` la vieja).
- **Un bucket de Supabase Storage no se revierte con `DELETE FROM storage.buckets` (ni ningún otro DML directo sobre tablas de Storage) — Supabase lo bloquea a propósito** (trigger `storage.protect_delete()`: "Direct deletion from storage tables is not allowed. Use the Storage API instead."), confirmado al intentarlo con la 019 (CC-049). El ciclo "aplicar → probar → revertir → reaplicar → probar" de esta fase **no aplica igual a una migración de Storage**: para borrar un bucket de verdad hace falta el dashboard o `supabase.storage.deleteBucket()` (Storage API), ninguno disponible desde las herramientas MCP de esta sesión. En su lugar, cada migración de Storage se escribe **idempotente** (`ON CONFLICT (id) DO UPDATE`, no `DO NOTHING`) y se verifica reaplicándola sobre el bucket ya existente, confirmando que la configuración queda correcta — esa reaplicación hace las veces de la prueba de "revertir y reaplicar" para este tipo de migración. La 019 se aplicará con el mismo archivo, sin cambios, cuando llegue la Fase 8 (`valpo-verde-conecta`, issue #45) — la idempotencia es justamente lo que permite correrla ahí sin preocuparse de si el bucket ya existe.
- **Las llamadas a funciones SQL con varios parámetros del mismo tipo se escriben siempre con notación con nombre (`p_x => valor`), tanto en los scripts de prueba como en el backend.** Detectado el 2026-10-25 al escribir la 018i: las pruebas de `fn_create_tree_alta` (10 parámetros, varios `text`/`numeric` consecutivos) usaban notación posicional en `pruebas_018d_alta_version.sql`, `pruebas_018e_inspection_draft.sql`, `pruebas_018g_transicion_estados_ot.sql` y `pruebas_018h_crear_ot.sql` — sin inversión real en esos 4 archivos (A4/A6 verificados, correctos), pero la 018i nueva sí tenía `p_especie_cientifica`/`p_nombre_comun` invertidos. Las 14 llamadas (más `fn_rename_species`/`fn_complete_species`/`fn_resolve_or_create_species`/`crear_usuario_prueba` en la 018i) se convirtieron a notación con nombre en los 5 archivos. El backend (`supabaseAdmin.rpc("fn_x", { p_y: ... })`) ya es seguro: `supabase-js` pasa el objeto como parámetros con nombre de Postgres, no por posición — verificado en todos los repositorios de `src/repositories/sivu/` y en `tree.repository.ts` (demo vieja).
- **El md5 de una migración aplicada se compara contra el archivo pasado a LF** (`tr -d '\r' < archivo.sql | md5sum`), no contra el archivo tal como está en disco: los archivos del repo tienen finales de línea CRLF (Windows) y lo que se envía con `apply_migration` va con LF. Lo aplicado se lee con `SELECT md5(statements[1]) FROM supabase_migrations.schema_migrations WHERE version = '…'` (o `md5(pg_get_functiondef(...))` / `pg_get_viewdef` para un objeto suelto). Fuera de los finales de línea, el contenido tiene que ser idéntico.
- **`execute_sql` no queda en el historial de migraciones de Supabase (`list_migrations`); `apply_migration`, sí.** La herramienta `apply_migration` del MCP falló dos veces consecutivas con `Invalid or expired requestState` al revertir la 018f (2026-10-24, justo al cruzar la medianoche de la sesión) — se reemplazó por `execute_sql` para no bloquear el trabajo, y eso dejó el historial de migraciones desincronizado del estado real de la base durante casi un día (`fn_transition_work_order_estado` viva con la corrección de D-241, pero el historial marcándola como borrada). **Corregido el 2026-10-25:** revertida y reaplicada la 018g otra vez, esta vez solo con `apply_migration` (falló una vez más con el mismo error transitorio, el reintento funcionó) — `list_migrations` vs. estado real 018a–018h, cero diferencias. **Regla correcta: `execute_sql` es solo para pruebas y consultas de solo lectura — nunca para aplicar o revertir una migración.** Si `apply_migration` falla, **reintentar `apply_migration`**; nunca sustituirlo por `execute_sql` para que el cambio quede en el historial.
